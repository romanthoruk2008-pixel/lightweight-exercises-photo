Не використовувати `catalog.image.origin` як походження нового PNG: цей
історичний каталог також має `gym_visual_edit`, що не описує нові прийняті
генерації. Не змінювати `content`, `name`, `attribution` або користувацькі
таблиці під час оновлення image-полів. Попередньо зберегти snapshot старих
image-полів та `updated_at` для відкату/перевірки конкурентних змін.

## `replaces_ids`: встановлене і невідоме

Результати SQL Editor, надані користувачем: JSONB, NOT NULL,
default `'[]'::jsonb`, comment NULL. Повні 8 CHECK definitions збережені
у `sql_editor_evidence.json`. `catalog_exercise_lists_are_arrays` вимагає
масиви у `secondary_muscles` і `replaces_ids`; об'єкт/скаляр/JSON null не
проходять це правило. CHECK не перевіряє тип елементів `replaces_ids`,
існування цих ID чи напрямок заміни. Їхню семантику не встановлено.

Поле й replacement-related ключі відсутні в усіх 451 записах джерела.
У checkout немає схем SQL, міграцій або коду апки, які визначають його
семантику. Результат перевірки оригінального working-manifest з release
збережено в `source_archive_inspection.json`.

Користувач відповів, що репозиторій/міграції, призначення й значення поля
йому невідомі, та прямо вказав позначити поле невідомим і не заповнювати
навмання. Після отримання SQL default і CHECK підготовлено чернетку insert
без поля `replaces_ids`; жодного значення від агента не підставлено. Для
локальної перевірки CHECK враховано фактичний DB default порожнього масиву.
Це технічно допустимий default, але не рішення про заміни вправ: бізнес-
семантика залишається блокуванням перед реальним імпортом. Повторно
питання про репозиторій не ставиться.

Чернетка містить всі 451 source records із незмінним `content`, без
`updated_at` (server default), з усіма п'ятьма image-полями NULL. Усі
вісім правил локально проходять для цих ефективних рядків і для повних
image patch 135 прийнятих PNG. Зокрема `image_all_or_nothing` забороняє
часткове оновлення п'яти image-полів; їх потрібно змінювати разом.

## Порядок майбутнього імпорту

1. SQL count=0 без RLS, default і 8 CHECK вже підтверджені. Перед майбутнім
   записом повторити актуальний read, щоб виявити появу нових записів;
   повторно запитувати вже надані результати зараз не потрібно.
2. Отримати семантику/значення `replaces_ids` із підтвердженого джерела.
3. Повторити dry-run. Для наявних ID порівняти всі поля й переклади;
   конфлікти блокують імпорт. Не використовувати сліпий upsert.
4. Лише після окремого дозволу: вставити відсутні записи каталогу з точними
   ID та незмінним `content`. Підтвердити 451 ID/4448 блоків і їх hashes.
5. Для 135 PNG перевірити Storage destination. Якщо там є object, прочитати
   його байти та звірити SHA256. Той самий файл пропустити; інший блокувати.
   Завантажувати нові objects з `image/png` та без перезапису.
6. Після підтвердженого завантаження оновлювати тільки image-поля одного
   точного ID; при конкуренції `updated_at` або старих image-полів зупинитися.
7. Перевірити public URL, відповідність БД, клієнтські читання та відсутність
   змін мовних блоків. Каталог і PNG на GitHub не переписувати.

## Апка і права

Апка зберігає у БД шлях відносно bucket і отримує URL через
`supabase.storage.from('exercise-images').getPublicUrl(image_path)`.
Public object URL: `/storage/v1/object/public/exercise-images/<image_path>`.
Admin secret не передається клієнту. Читання каталогу звичайним клієнтом і
запис shared PNG потребують окремої перевірки policies/grants; права
звичайного клієнта та поведінка апки поки не перевірені.
