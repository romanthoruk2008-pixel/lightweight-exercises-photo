# Правила роботи з вправами та зображеннями

## Початок і контекст

- Спочатку читати `docs/handoff.md`, `docs/exercise-image-workflow.md`, `docs/exercise-image-style.md` та workflow у `data/exercise-image-progress.json`.
- Працювати лише в поточному хмарному середовищі та існуючому checkout; не використовувати локальний комп’ютер користувача і не створювати Git worktree без запиту.
- Перевіряти доступність джерел/референсів/результатів: файли попередньої задачі не гарантовано доступні. За відсутності повідомляти конкретний блокер.
- У контекст читати лише ID поточної вправи або малого пакета. Для пілоту — англійські description/instructions/cues/mistakes/safety, обладнання й м’язи. Скрипт може прочитати JSON для вибірки, але не виводити весь каталог, переклади, архів чи довгі журнали.
- Каталог не змінювати: 451 ID, 4448 мовних блоків, історія й null. Не перейменовувати/об’єднувати вправи. 3 архівні лишаються `blocked_archived` без окремого рішення.

## Референси й техніка

- Перед першою генерацією відкрити всі прикріплені зображення й коротко зафіксувати ролі: зовнішність/анатомічний стиль; поза/обладнання/подача; палітра UI. Якщо пікселі недоступні — не генерувати навмання.
- Hevy використовувати для подачі й обладнання; його UI у результат не включати. Палітру UI не переносити автоматично на тіло/тренажер.
- 48 історичних PNG не використовувати як результати чи стилістичні еталони. Історію зберігати окремо. Untouched `existing_needs_review` без нових результатів перевести в `not_started`; не скидати виконану нову роботу.
- Спиратися на техніку, не лише назву. Не вигадувати насадки, хват, опори, положення тіла чи фази. Неоднозначність → `needs_clarification` із конкретною причиною.
- Стиль пілоту — v1 із style; остаточно його затвердить користувач після пілоту. Кожна спроба прив’язана до версії, вихідного ID та потрібних референсів.

## Поточний пілот

Порядок: `bench-press-barbell`, `biceps-curl-dumbbell`, `seated-shoulder-press-machine`, `cable-fly-crossovers-machine`, `ab-wheel`.

- Пілот дозволено; повторний дозвіл не потрібний. Референси й достатня техніка — необхідні передумови. 5 окремих зображень, без загального колажу.
- Лише вбудований `image_gen.imagegen`; не використовувати платний OpenAI API або сторонні платні сервіси. API-ключ/SDK не є вбудованим інструментом. Якщо інструмент недоступний/ліміт вичерпано — зберегти progress/handoff, повідомити, не змінювати спосіб.
- Перші 2: одна коротка візуальна перевірка кожного, максимум 3 пункти (техніка/анатомія/хват/опори; обладнання; стиль/підсвітка/композиція). За явної помилки дозволено одну корекцію; максимум 2 генерації на ID. Нерозв’язана помилка → `needs_fix`.
- Вправи 3–5: **не проводити агентську візуальну перевірку після генерації**; `agent_visual_review = not_performed`. Автоматичні повтори заборонені. Правильний prompt за технікою обов’язковий.
- Для всіх 5 — файлові перевірки: відкриття PNG, реальні dimensions/квадратність, alpha, прозорі фонові пікселі, ID/path/hash. Alpha сама по собі не доводить прозорість. Помилка → `technical_issue`; для 3–5 без додаткової генерації.
- Розділяти `technical_check` (null до виконання, далі passed/failed), `agent_visual_review` (passed/needs_fix/not_performed), `user_review` (pending до рішення). Не позначати approved/accepted без явного рішення користувача.
- Зберігати prompt, ID, style version, кожну фактичну спробу й result path поза Git; progress оновлювати після кожної вправи. Підготовка prompt не збільшує attempts. Прийняте не перегенеровувати без запиту.
- На пілоті зупинитися: показати всі 5 результатів із назвами; для 3–5 зазначити «Візуально не перевірено — для перегляду користувачем». Масова генерація, Supabase та push зараз не дозволені.

## Продовження й зберігання

- Після переривання звірити progress з outputs, ID, хешами й версіями стилю. Не повторювати виклик лише через `in_progress`; відсутній файл не вважати готовим. Не скидати attempts/історію.
- Оновлювати handoff після пакета, контрольної точки чи переривання. Після прийняття пілоту майбутні пакети — до 30, контрольні точки кожні 10; режим перевірки узгодити тоді, не застосовувати автоматично стару вимогу переглядати кожне зображення.
- Не запускати окремих агентів лише для файлових перевірок. Не повторювати перевірки без причини.
- Архіви/медіа/результати тримати поза Git; не обходити `.gitignore`. Джерела не змінювати. Supabase — після окремого налаштування/дозволу, тільки прийняті результати; шляхи не вигадувати.

## Уточнення користувача для продовження пілоту

- Вкладення використовувати **лише для зовнішності, пропорцій, матеріалів і деталізації**. Позу, обладнання й м’язову підсвітку визначати заново з англійського каталогу; не копіювати їх із скриншотів. Це уточнення замінює попередню роль Hevy як технічного еталона.
- Перед викликом сформулювати конкретні положення кінцівок, хват, опори, обладнання, характерну фазу й ракурс. За відсутності бренду дозволена стандартна сумісна конструкція; не вимагати фото тренажера й не додавати елементів, що змінюють вправу.
- Перед **кожним** викликом перечитати progress. `approved` / `uploaded` пропускати, крім прямого запиту повтору. Якщо прийнятий файл відсутній або його hash не збігається — повідомити, не генерувати заміну.
- Після явного прийняття користувачем: `user_review = approved`, загальний status = `approved`, точні accepted file path/SHA256 і запис рішення в progress та handoff. Агентська оцінка не є прийняттям. До рішення `user_review = pending`.

## Правка після перегляду пілоту

- Користувач прийняв Bench Press **attempt-1**, Bicep Curl, Cable Fly та Ab Wheel. Зберігати точні прийняті файли без змін; не підміняти Bench Press другою спробою. Технічні невідповідності та попередні оцінки залишати в історії.
- Прямий запит дозволяє лише одну нову спробу Shoulder Press (attempt-2) через артефакти тренажера. Два нові скриншоти з повідомлення про правки — еталон його конструкції для цієї корекції. Інші зображення не перегенеровувати.
- Для нового Shoulder Press виконати лише файлові перевірки; `agent_visual_review = not_performed`, `user_review = pending` до рішення користувача. Автоматичних повторів не робити.

- Наступний прямий запит дозволяє одну точкову корекцію Shoulder Press **attempt-3**: дві ручки, кожна на своєму цілісному важелі. Attempt-2 відхилено користувачем через відсутню ручку/з’єднання. Вимога 1024×1024 залишається без змін; не виконувати автоматичний ресайз або повтори через розмір. Перевіряти фактичну прозорість.

- Пілот завершено: користувач прийняв Shoulder Press attempt-3; тепер усі п’ять результатів `approved`. Не повторювати попередні корекції. Наступний етап, масові пакети, Supabase і push потребують окремого запиту.

## Резервні копії прийнятих результатів

- Для backup відбирати лише user_review=approved та саме accepted_path/accepted_sha256; поточний result_path може бути іншою неприйнятою спробою. Не генерувати заміну за відсутності файла.
- Backup status зберігати окремо від user_review та Supabase. Локальна ZIP-копія або GitHub asset не означає uploaded_to_supabase.
- Manifest зв’язує exercise_id із незмінним повним catalog.json; PNG paths у ZIP відносні. URL asset записувати лише після фактичної публікації та перевірки SHA256. Невідомі batch_id або час схвалення залишати null.
- Перед продовженням у новій задачі завантажити доступну резервну копію за реальним asset URL та звірити SHA256; не покладатися на шляхи /workspace попередньої задачі.

## Прямий запит на PNG у Git

Користувач окремо дозволив зберегти 25 прийнятих PNG із data/approved-images-manifest.json у assets/exercises/<exercise_id>.png гілки work. Це вузький виняток із заборони медіа в Git; SHA256 та байти прийнятих файлів зберігати без змін. Інші медіа, ZIP і вихідні архіви лишаються поза Git. Позначати GitHub backup перевіреним лише після fetch віддаленої work та звірки кожного PNG за manifest; ця дія не змінює Supabase status чи user_review.
