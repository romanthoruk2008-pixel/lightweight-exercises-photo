## Перед генерацією

1. Відкрити всі прикріплені референси **один раз**; записати фактичні ролі/хмарні шляхи у style. Якщо пікселі недоступні — повідомити, не генерувати. Старі PNG не підставляти.
2. За референсами визначити модель, кількість поз і подачу руху. Палітра UI не задає кольори тіла/тренажера; UI Hevy не включати в output.
3. Prompt поточного ID — за англійською технікою, м’язами/обладнанням і v1. Передавати потрібні візуальні еталони; не повторювати аналіз усіх вкладень.
4. Cable Fly Crossovers: після уточнення користувача дозволена стандартна сумісна конструкція за текстом. Обрано стоячий горизонтальний fly з блоками на рівні грудей/плечей, окремими D-руків’ями й без додаткової грудної опори. Це вибір сцени за текстом, не техніка з референсу; needs_clarification знято.

## Виклик і збереження

- Лише вбудований `image_gen.imagegen`; без платного OpenAI API/інших платних сервісів. Перевіряти фактичну наявність tools, не API-ключ/SDK.
- Референси/результати зберігати поза Git в `/workspace/exercise-image-pilot-v1/`. `pilot-plan.json` містить тільки 5 англійських записів і заблоковані draft prompts; це не outputs.
- Перед викликом записати `in_progress`, ID, prompt, tool, reference paths, `style_version = v1`, час/номер спроби в `attempt_history[]`; збільшити attempts. Підготовка prompt та перевірки не є спробою.
- Після виклику зберегти output в каталозі відповідного ID, записати result path/SHA256 і результат/помилку спроби. Одразу оновити progress.
- Якщо tool недоступний/ліміт вичерпано — зберегти progress/handoff, повідомити й зупинитися; не переходити на API. Перерваний виклик спочатку звірити з outputs, не повторювати автоматично.

## Перевірки

**1–2:** одна коротка візуальна перевірка, до 3 пунктів: техніка/анатомія/хват/опори; обладнання; стиль/підсвітка/композиція. За явної помилки дозволено одну корекцію, максимум 2 генерації на ID. Невирішена помилка → `needs_fix`.

**3–5:** після генерації не відкривати/не аналізувати зображення для агентської візуальної перевірки; `agent_visual_review = not_performed`. Автоматичні повтори заборонені; правильний prompt усе одно обов’язковий.

**Усі 5:** `scripts/check_exercise_image.py ID` (read-only, після запису нового result path/hash у progress) перевірити PNG/відкриття, квадратність, реальні dimensions (ціль 1024×1024), alpha, фактично прозорі фонові пікселі та ID/path/hash. Alpha без прозорих пікселів недостатня; піксельні перевірки не оцінюють техніку чи анатомію. Невідповідність → `technical_issue`; для 3–5 без повторної генерації.

| Поле progress | Значення |
| --- | --- |
| `technical_check` | null до перевірки; далі passed / failed |
| `technical_check_details` | dimensions, alpha/background metrics, ID/path/SHA256, помилки |
| `agent_visual_review` | passed / needs_fix / not_performed; для 3–5 завжди not_performed |
| `agent_visual_review_notes` | до 3 пунктів для 1–2; без вигаданої оцінки 3–5 |
| `user_review` | pending до рішення користувача |
| `result_sha256` | null до output, потім SHA256 файла |

Історичні `historical_image`, `existing_image`, mapping та старе `visual_review` не є прийняттям нового output. Нова оцінка розділена у полях вище. `generated_needs_review` означає очікування користувача; `needs_fix`/`technical_issue` — проблеми. Не ставити approved/accepted без явного рішення користувача.

## Завершення

Показати всі 5 результатів із назвами, короткі оцінки 1–2; для 3–5 — «Візуально не перевірено — для перегляду користувачем». Повідомити technical issues, оновити handoff і **зупинитися на пілоті**. Якщо генерацію заблоковано, не видавати drafts/старі PNG за результати.

Після перегляду користувач може прийняти v1 або задати корекції й дозволити наступний етап. Майбутні пакети до 30, контрольні точки кожні 10; режим перегляду узгодити окремо. Supabase — після окремого налаштування/дозволу, тільки прийняті результати. Push зараз заборонено.

Перевірка каталогу/progress із кореня checkout:

```bash
python3 scripts/build_exercise_catalog.py /workspace/exercise-source-v1/extracted/exercise-catalog-v1 --verify-only
```

У новій задачі перевірити доступність джерел, референсів і outputs; не отримувати їх із комп’ютера користувача. Після переривання звірити ID/path/hash/style version й журнали перед повтором.

## Уточнення користувача для продовження пілоту

- Вкладення використовувати **лише для зовнішності, пропорцій, матеріалів і деталізації**. Позу, обладнання й м’язову підсвітку визначати заново з англійського каталогу; не копіювати їх із скриншотів. Це уточнення замінює попередню роль Hevy як технічного еталона.
- Перед викликом сформулювати конкретні положення кінцівок, хват, опори, обладнання, характерну фазу й ракурс. За відсутності бренду дозволена стандартна сумісна конструкція; не вимагати фото тренажера й не додавати елементів, що змінюють вправу.
- Перед **кожним** викликом перечитати progress. `approved` / `uploaded` пропускати, крім прямого запиту повтору. Якщо прийнятий файл відсутній або його hash не збігається — повідомити, не генерувати заміну.
- Після явного прийняття користувачем: `user_review = approved`, загальний status = `approved`, точні accepted file path/SHA256 і запис рішення в progress та handoff. Агентська оцінка не є прийняттям. До рішення `user_review = pending`.

## Backup і відновлення

Відбирати тільки user_review=approved, використовувати accepted_path та accepted_sha256. У ZIP зберігати незмінні PNG, повний каталог 451/4448 і manifest з відносними PNG paths, exercise_id, SHA256, MIME, dimensions, style та відомим часом схвалення. Локальну перевірку, публікацію Release та Supabase зберігати окремо. Створювати лише новий вільний тег/asset, без перезапису; після завантаження звірити фактичний asset SHA256. Якщо API недоступний — зберегти ZIP і явний блокер; URL лишити null. Для відновлення брати asset URL із manifest, перевірити ZIP та кожен PNG; локальні шляхи старої задачі не є постійними посиланнями.
